🔎 Deep-dive: what's wrong in fact_sales.order_ts_utc, and the fix

The issue: the migration re-timestamped every order to "UTC" by adding a fixed +5 hours, but the Snowflake source was already the canonical time. So every order is shifted 5 hours forward.

  • Correct (Snowflake source): order_ts_utc = order_ts  (already canonical)
  • Migrated (target, revenue_target.sql:32): order_ts_utc = r.order_ts + INTERVAL 5 HOURS
  • Why it matters: a fixed offset is not a timezone conversion. Orders near end-of-day roll onto the next calendar day, so anything grouped by day — daily sales, daily revenue, day-over-day trends — is wrong, even though row counts and totals reconcile.

Proven, not guessed: the deterministic drill-down ran a confirming query and found a single distinct offset of exactly 5.00 hours across every order present — the signature of a constant shift, not a genuine timezone/DST conversion → migration-induced, 98%, query-confirmed. UC lineage: source order_ts.

The fix — drop the fixed +5h (or use a real timezone conversion), then re-run reconcile:

-- revenue_target.sql:32 — corrected order_ts_utc
r.order_ts AS order_ts_utc
-- or, if a real conversion is intended (e.g. US/Eastern → UTC):
convert_timezone('America/New_York', 'UTC', r.order_ts) AS order_ts_utc

Re-run Lakebridge reconcile on fact_sales → the difference clears. Owner: migration engineer.

Supporting findings (same recon, same clean treatment): fact_sales — ~1,000 orders missing (WHERE order_id % 500 <> 0), a stray load filter (why Rows matched is 99.8%); unit_price landed as DECIMAL(18,2) vs source DECIMAL(18,4) — precision/scale loss; dim_customer.customer_name — UPPER(TRIM()) vs proper case — string-format.

Backup — if asked
  • Is this AI? Not for this recon — every finding is deterministic: a rule fires, then a confirming query proves it. Hybrid mode adds a Foundation-Model tier only for the hard, hand-tweaked transforms; even then the model proposes a cause + a query, and the verdict sticks only if the query confirms. Worst case → needs-review, never a wrong answer.
  • Does it scale? RCA runs on the bounded recon sample, not raw volume — 500k rows here, tens of millions elsewhere, root-caused in ~90s.
  • Where do the scripts come from? trace_job auto-discovers the building job's SQL from UC lineage; source values/types come from the recon output — no manual script-passing.
  • How is a difference classified? migration-induced (fix code), genuine-data (route to owners), expected (no action), needs-review (investigate). "Actionable" = migration + genuine.
