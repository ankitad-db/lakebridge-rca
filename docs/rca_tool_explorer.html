The judgement

Four verdicts — the migration-vs-genuine call

The value AVF and plain reconcile can't make for you: is this a defect to fix in the migration, or a real data change to route to the owner?

🔧

Migration-induced

Introduced by the migration/transform (scale loss, tz shift, transpile). Fix in the pipeline.

📊

Genuine data difference

A real upstream data change (drift, late data). Route to the data owner.

✅

Benign / expected

Explained & acceptable (e.g. known rounding within tolerance). No action.

🔍

Needs review

No probe fired with confidence → handed to the live drill-down / LLM tier. Investigate.

How the two tiers divide the work

Deterministic first, agentic only for the residual

The engine is repeatable and cheap by default. The LLM is a fallback that widens coverage — and it never gets the final word without a confirming query.

🧮 Deterministic engine — always on
  • Probe-based classification into 8 categories + dialect knowledge base
  • Live drill-down queries that confirm each hypothesis on real rows
  • Distribution-drift, depth-agnostic UC lineage trace-back, downstream blast-radius
  • Systemic clustering ("fix one, resolve many")
  • Runnable fix generation + a validation gate that dry-runs the fix
  • Learning-loop memory of confirmed causes; append-only audit trail
🤖 Agentic tier — residual only
  • Runs only for needs-review / unknown findings the probes couldn't grade
  • Proposes a hypothesis and a confirming SQL query from the evidence bundle (incl. lineage trace-back)
  • The query is executed; the verdict is promoted only if it confirms
  • Authors the grounded plain-English "Analyst summary" in the notebook
  • In Genie Code: the in-workspace agent; in the App: the Foundation Model API
  • Same guarantee as Tier-1: no verdict without an executed query

The use case

Reconciliation flags the symptom — ReconResolve finds the upstream cause

A retail Orders dataset is migrated Snowflake→Databricks through a layered pipeline (raw → enriched → curated → gold). The team reconciles the two published gold tables against the trusted source. Reconciliation tells you which columns and rows differ — but not why, and not that several "different" columns actually share one upstream cause. That triage is the manual bottleneck this removes.

Reconciled: orders_src  vs  orders_gold_c & orders_gold_d   recon_id 7d786327137d44c9bef3f2bc75fba518

Only the two gold leaves are reconciled — yet every real defect lives one or two layers upstream. The engine must walk back from the symptom on the leaf to the layer where the difference actually entered.

⚙️ How the RCA behaves

1
Ingest the flagged mismatches

Reads the reconcile output — the columns/rows that differ on each gold leaf.

2
Fingerprint each difference

A probe + the Snowflake knowledge base assign a category (precision, timezone, string, volume…).

3
Confirm on real rows

A live drill-down query must agree before any verdict is trusted.

4
Walk lineage upstream

Hop by hop past the leaf to the layer where the difference actually entered.

5
Collapse shared causes

Differences tracing to the same upstream defect cluster into one root cause.

6
Cite the code & propose a fix

Reads the migrated SQL for the exact transform, then suggests a dry-run-validated fix.

The takeaway: only the two gold tables were reconciled, but none of the six issues originate there. Four of them (both amount + both order_ts) collapse to a single upstream defect in orders_enriched; the other two are arm-specific. Fixing one enrichment step clears four findings across two tables — which reconciliation alone could never tell you.

Deterministic first · agentic fallback · proven live

Two tiers on one payments migration — the mechanical fix vs. the judgement call

A retail payments table migrates Snowflake → Databricks. Reconciliation flags two columns. One has a clean fingerprint and is graded deterministically; the other is a silent business-logic regression no probe can name, so it is handed to Claude, which proposes a hypothesis and a confirming query — and only promotes the verdict if that query passes.

✅ Verified live — recon_id 9253e330…4803e on mig_demo_payments, Foundation Model endpoint databricks-claude-opus-5. 500 rows · join payment_id. Clean controls (customer_id, gross_amount, currency, status) produced no finding.
🧮 Tier 1 · Deterministic — payment_ts
payment_ts differs on all 500 rows by a constant +5:30
  • The temporal probe recognizes the constant, known offset → category timezone.
  • A live drill-down query confirms the shift holds on the flagged rows.
  • Root cause: the migrated load never normalized the session timezone to UTC.
  • Fix: "normalize to UTC on load" — a runnable, gate-validated suggestion.
verdict → 🔧 timezone / migration_induced no LLM involved · repeatable · cheap · same result every run
🤖 Tier 2 · LLM fallback — net_amount
net_amount differs — but by no offset, rounding, scale, or string pattern
  • Source rule: net = round(gross×0.90,2) (10% discount). Target shipped round(gross×1.08,2) (8% tax) — ratio ≈ 0.83, not a clean factor.
  • No probe fingerprints it → the deterministic tier is honest: needs-review / unknown.
  • Claude (Opus 5) gets the evidence bundle (samples + the migrated derivation), back-solves both formulas, and writes an exact-reconstruction confirming query.
  • The query runs and passes → promoted to transpilation / migration_induced.
Claude's confirming query (executed, returned confirmed=TRUE): count_if(NOT (t.net_amount <=> ROUND(s.gross_amount*1.08,2))) = 0 -- target uses ×1.08 AND count_if(NOT (s.net_amount <=> ROUND(s.gross_amount*0.90,2))) = 0 -- source used ×0.90 → 🔧 transpilation / migration_induced — the changed rate constant, query-proven
🔒 The gate held, live: Claude's first hypothesis used a ratio heuristic and its query returned confirmed=FALSE → the finding stayed needs-review. Only the exact reconstruction promoted it. The query is the gate — never an LLM guess.
Finding→ ◆ does a probe fingerprint it?
YES live drill-down confirms it on real rows → 🔧 verdict Tier 1 · deterministic (payment_ts)
NO Claude proposes a hypothesis + a confirming query → ◆ query confirms? → 🔧 verdict  ·  else 🔍 needs-review Tier 2 · agentic (net_amount)

Why it matters: the timezone bug is a known mechanical defect — caught cheaply and repeatably with zero LLM. The tax-vs-discount regression is exactly the kind of silent, business-logic drift that slips through migrations and manual review; the LLM names it and proves it with an executed query. Deterministic where it can be; agentic where it must be; query-gated always.
